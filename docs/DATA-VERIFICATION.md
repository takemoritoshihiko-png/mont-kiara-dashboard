# 住まいデータの調査・検証

本書は mont-kiara-dashboard の住所・商業施設・コンドミニアムを調査するときの手順。飲食店の採用条件は AGENTS.md が示す飲食裁定の正本を読む。データ欄や計算を変更する承認ではない。公開反映・一括データ操作・削除の確認条件は AGENTS.md と共通原本を保持する。

## 全調査の共通条件

- 対象一覧の全項目を確認する。未取得・情報衝突・対象外を理由付きで残し、推測で埋めない。実際に開いた出所・確認日・対象欄・旧値と提案値を記録する。
- 取得元の主張と確認済み事実を分ける。公式・物件単位の情報を優先し、同じ転載を独立した複数根拠と数えない。食い違いは追加確認または未確定とする。
- サイトの403/429や掲載量は調査時点の状況。旧ノートの到達可否や所有者一覧を現在の事実としない。アクセス制限やツールの禁止を迂回しない。
- 並行調査は対象を重複させず、書込みはメインへ提案を集約する。体数・1体の件数は対象量・競合・レート制限で決め、過去の固定件数を現在の義務にしない。
- 適用前に名前・ID・欄の意味・根拠を突き合わせる。異常値検査は再確認の入口であり、値を自動補正する根拠ではない。CSV変更後は AGENTS.md の検証を実行する。

## 住所と座標

1. 建物名と別名で建物単位を確認する。Nominatim の建物検索、EdgeProp の該当物件に埋め込まれた座標、Mapcarta/OSM 建物形状、公式サイトの Waze/Google Maps リンクを候補とする。使用時の提供条件を確認し、Nominatim は約1リクエスト/秒を上限目安に共有し、429なら連打せず別根拠へ移る。
2. 建物単位の独立した複数根拠を照合する。道路名だけの検索・道路中点・poskod.com を座標修正に使わない。検索結果の名前一致だけで確定しない。
3. 検証できなければ既存CSV値を維持し未確認と記録する。近接していても同一開発の別棟を勝手に同じ座標にしない。
4. 既存値から緯度/経度約0.003度（約300m）以上ずれる提案は再確認する。正しい建物に対する根拠が必要で、距離閾値だけで正誤を決めない。

由来と全文: [住所の旧調査記録](archive/rule-memory/feedback_address_verification.md)。Pavilion Hilltop を道路中点で約440m移してしまった事故が禁止の根拠。共有メモリの旧候補欄に残った poskod 記載は、この明示禁止へ整合させた。

## 商業施設

- 調査前に閉店・改名・再開発を施設単位で確認する。似たブランド/系列・所有者と運営者を混同せず、公式/運営者/REIT資料等の出所と時点を残す。旧オーナー一覧は探索候補だけに使う。
- 名称と読み: 公式英名を基に表記を揃え、日本語は音に忠実なカタカナ。閉店前の別名称を現行名として混ぜない。
- 開業年: 当初開業と増築・改装・再開業年を区別する。最新記事の日付を開業年にしない。
- 店舗数: 現在営業するテナント数と設計上の収容店数を分ける。CSVと検証値が30%を超えて異なる場合はフラグを立て、媒体間の食い違いも時点・定義を再確認する。
- 面積: retail NLA を対象とし、総延床面積GFAや住宅・駐車場込みと混ぜない。平方フィートと平方メートルを明示し、換算は 1㎡=10.764sqft。
- developer欄の調査は、この案件で使う現在の所有者/運営者の定義を確認してから行う。竣工時デベロッパーと同じとは限らない。
- 主なテナント: 施設の現行ディレクトリ等でアンカーの実在を確認する。系列ブランドから推測しない。複数名の区切りは既存形式のセミコロンに統一する。
- URL: 各候補を実際に開く。検索リンクや閉鎖ページを公式サイトとして確定しない。独自サイトが無いと確認できた場合と未取得を区別し、運営者の施設ページ等の代替根拠を記す。
- 全欄を再走査し、住所/座標・開業/状態・面積/店舗数・所有者・URLの不整合を確認する。修正件数だけで調査完了にしない。

由来と全項目の旧記録: [商業施設の旧調査記録](archive/rule-memory/feedback_commercial_data_verification.md)。当時の施設数・所有者例・アクセス表・調査件数は履歴。

## コンドミニアム

- 名前、住所、座標、デベロッパー、竣工年、住戸数、棟数、階数、専有面積、土地保有形態、売買価格、賃料、設備、URLを対象欄に沿って確認する。建物が似ている、近接している、同じ系列という理由で値を流用しない。
- 年: 完成年と予定年を区別する。予定年が過ぎただけで完成と断定しない。総戸数は住宅住戸、棟数は実体のタワー、面積は built-up（専有）を対象にし land area と混ぜない。
- 階数・棟数・戸数・面積の関係を確認する。低層・ヴィラ等の正当な例外は異常として書き換えない。面積の最小/最大が等しい場合も根拠を確認する。
- Freehold/Leasehold は該当物件の根拠で確認する。永遠に変わらないという旧説明だけで確認を省かない。
- 売買価格は時点・通貨・面積基準を揃え、直近12か月の資料を探索する。媒体差約15%、賃料差約20%などは再確認の目安で、範囲内なら正しいという保証ではない。旧エリア別価格帯を現在値にしない。
- 未完成物件の賃料や未取得価格を0円として表示しない。実際のゼロと不明を区別する（現行 AGENTS.md のデータ契約が正）。
- 設備は明記された事実を確認する。private liftは住戸専用のリフトロビー、conciergeは専任サービス、sky loungeは屋上等の共用設備、EV充電は実際の充電設備を確認する。poolを含む各設備をブランドや物件グレードから推測しない。設備値は0/1、low_densityだけ0〜3という既存区分を保持する。
- premium_score の式は AGENTS.md が正: private_lift×7 + concierge×2 + low_density + pool + sky_lounge + ev_charging（最大15）。単純合計へ戻さない。low_density は住戸数÷階数÷棟数を基に、1階あたり8戸超=0、5〜8戸=1、3〜4戸=2、1〜2戸またはヴィラ=3という既存基準を保持する。採点の調査を委譲するときは、この加重式と定義を指示書に含める。混合棟など当てはめが曖昧なら勝手に式を変えず未確認を記す。
- デベロッパーのブランド評価は、この案件の内部編集基準であり外部の客観的事実と表現しない。既存の親ブランド名と定義の完全一致、CSVの正のbrand_scoreが既定のブランド表に優先する契約を保持し、AI独自の採点に置き換えない。出所、表記、URL、未確定を含め全対象を検品する。

由来と全項目の旧記録: [コンドの旧調査記録](archive/rule-memory/feedback_condo_data_verification.md)。旧記録の『pool=0はほぼ誤り/既定1』と調査による確認義務、未完成賃料0と不明値表示の関係は未裁定部分を含む。前者を今回の自動補正命令にしない。low_density閾値やブランド採点の変更裁定は今回行っていない。

## 履歴の読み方

archive/rule-memory の3原文は当時の詳細・具体例・件数・未裁定表現を失わないための全文保全。新しい修正を承認する文書ではない。未裁定の強い旧指定と現行正本が衝突したら、操作前に既存決定の根拠を確認し、不足は未裁定のまま残す。
