> 竹森氏の指示「どういう筋道でその結論を出したのか、プロセスをアプリの中で経緯としてメモしておく」に基づく。

## 0. 何が問われたか（経緯）

1. 2026-08-08、外部意見書「KL飲食店インテリジェンス設計書」を受領。骨子=①ミシュランKL版は構造的に偏る（セランゴール圏外・マレー料理僅少・屋台ゼロ・鮮度問題）②統合スコアを作るな、独立ソースの一致を数えろ③判断は家族のログにしかない。
2. 竹森氏の目的定義: **「飲食の美味しいお店だけをピンポイントで行くアプリ」**。
3. 補足裁定: **ミシュランは完全網羅のままでよい。ただし別軸で「本当に美味しい」が推奨されれば100点**。
4. AIの初回提案（68点）と再提案（88点）は、①既存台帳の鮮度劣化対策の欠落 ②「金曜の夜どこ行く」場面への最適化不足 を自己指摘して作り直した。本メモはその最終検討の記録。

## 1. ゼロベースの気づき: 網羅とピンポイントはベクトルが逆

- 完全網羅 = recall最適化（取りこぼしゼロ）。2026-08-08朝に完了（現存する公式KLミシュラン75店を全収載）。
- 「美味しい店だけ」= precision最適化（ハズレゼロ）。**網羅の達成が自動的にピンポイントを壊す**: 網羅ゆえに Li Yen(★3.9)や Café Café(★4.1)のような「掲載はされているが群衆評価が弱い」店も台帳に入った。
- 解決 = **データは網羅、表示レンズは2枚**。台帳レンズ（全店・索引）と推奨レンズ（本当に美味しい確証がある店だけ）を分ける。データを消さずに目的を両立する。

## 3. 結論（推奨軸の設計）

1. **台帳=網羅（現状維持）**: ミシュラン全掲載+群衆枠。消さない。索引・資産。
2. **推奨=別軸のカテゴリバッジ（数値合成しない）**:
   - 🥇 **鉄板**: 家族が「また行く」= 最上位。外部が何と言おうと家族の判定が勝つ
   - ✅ **二重確証**: 独立の権威（ミシュラン/Tatler/50 Best）×群衆強シグナルが一致（36店）
   - 🎖 権威単独 / 👍 群衆単独
   - 🤔 **通好み**: 乖離あり・老舗大衆系（低評価の主因が味以外と裁定済み）
   - ⚠️ **要注意**: 乖離あり・裁定でも説明がつかない（推奨レンズから除外）
   - ⬜ 未確証（評価値なし）/ 🚫 閉店・休業（推奨レンズから自動除外）
   - 乖離8+疑問4店の裁定材料は検証Aの実勢調査による（本メモ末尾に結果を追記）
3. **家族の記録が唯一の「判断」**: 「もういい」= 外部評価に関わらず推奨から外す（家族拒否権）。
4. **鮮度の守り**: verified(最終確認日)+四半期の生存スイープ+12ヶ月言及なしチップ。閉店店の轍（Qureshi問題）を自分が踏まない。
5. **ローカル層の拡張**: 検証Cの44店級は「候補箱」（台帳外の軽いリスト）へ。昇格は家族実食のみ。
6. バー6店（50 Best）は別途裁定（10分類目 or 別レイヤー）。

## 4. 棄却した代替案と理由

- **統合スコアに推奨を織り込む**: 「どの質問にも答えない数字」になる（意見書3-1）。棄却。
- **Google値の足切りで推奨を作る**: Dewakan・老舗ホーカーを誤殺する（2-1実測）。棄却。
- **独立2クラスタ一致を推奨の必要条件にする**: ローカル層で重複ゼロの実測（2-3）により、ファインダイニング専用の物差しと判明。限定採用。
- **FSQ OS Places導入・L0マスタ**: 数百店規模ではrestaurants.jsonが既にマスタ。過剰装備。棄却。
- **家族4人別々の★**: 共有1ファイル運用が始まったばかり。スマホ運用開始時に再検討。保留。

## 5. 検証Aの結果（乖離店の実勢・2026-08-08帰還）と裁定案

直近12ヶ月のレビュー原文・専門筋の掲載継続を突合した結論:

| 店 | 低評価の真因（実勢） | 裁定案 |
|---|---|---|
| Dewakan(2★・4.2) | 価格期待値ギャップ+挑戦的な味+会計等フロント細部。**料理劣化なし・専門筋の支持は最も強固** | 🤔通好み（高額・挑戦的。万人向けでないと明記） |
| Li Yen(3.9) | 祝祭限定ビュッフェの品質ブレが低評価を集中生成。通常の点心・アラカルトは高評価(TA4.5) | 🤔通好み（条件: 祝祭ビュッフェを避ける） |
| Shanghai Restaurant(4.1) | ホテル価格vs一般客の価格感覚。劣化兆候なし・2026/2「人生最高の小籠包」 | 🤔通好み（価格覚悟） |
| Passage Thru India(4.3/TA4.0) | 団体ツアー流入時の待ち・ブレ。個人客のアラカルトは常連が支持継続 | 🤔通好み（条件: 団体時間帯を避ける） |
| Wong Mei Kee(3.8×2903) | **味でなく供給構造**（1日3時間営業に需要集中・支払い20分/提供40分待ち）。「変わらず美味しい」が多数派 | 🤔通好み（条件: 開店直後に行く） |
| Sek Yuen(4.1) | ノンエアコン+2026年初頭に単発の調理ブレ。老舗の味は維持が多数派 | 🤔通好み |
| Sri Nirwana Maju(4.1) | 混雑・駐車の構造不満（Wong Mei Kee同型）。ただし一次レビューの裏取り薄 | 🤔通好み（暫定・次回スイープで再確認） |
| Café Café(4.1) | **データ不足**（レビュー投稿頻度自体が低い店。直近一次情報を取得できず） | ⬜未確証扱い（推奨レンズから外す・次回スイープで再調査） |

**パターン結論**: 「権威×群衆の乖離」の実勢は (a)高級系=価格期待値+祝祭/団体運営ブレ (b)老舗大衆系=ミシュラン後の需要に供給が未対応、のどちらかで、**味の劣化が確認されたケースはゼロ**。⚠️要注意ティアは「裁定しても説明がつかない店」専用の空集合スタートとなる。これは規則が甘いのではなく、実勢調査が全店に説明を与えた結果である（将来の生存スイープで説明のつかない劣化が出たら初めて⚠️が入る）。

## 6. 実装への落とし込み（次の実装バッチの仕様）

## 11. 🗑非表示ボタン(2026-08-08・竹森氏依頼)

**依頼**: 「私の方で『ここは違うだろう』と思ったデータに対しては、気楽に消せるようにしてほしい」。AI側のピックアップにオーナーが拒否権を持つ仕組み。

**設計**: 物理削除は不採用(追い番R####の欠番再利用事故・家族記録との整合を壊す)。個人記録 `src/data/personal.js` に**7項目目のフラグh**を追加し、記録側で隠す。
- カードの記録ボタン列の右端に控えめな🗑(opacity .55・hoverで赤)。1タップで台帳・地図から消え、toastが戻し方を案内
- 復元=データ管理の「非表示にした店」節(0件なら節ごと非表示)。1タップで戻る
- filter層は `f.hiddenIds`(Set)で除外。**外食モード限定**(`eatoutActive()` ゲート) — 住まいモード(公開)はpersonal.jsを一切読まないモード分離契約を維持
- hは書き出し/読み込みの往復・ファイルDB書きスルーで他PCにも同期。h=1だけのエントリは「空」扱いしない(isEmptyEntry改定)
- テスト10件追加(personal 7+eatoutMode 3)=全680件green。実画面で hide→131→130→データ管理で戻す→131 の往復を確認

## 18. ミシュラン掲載店の可視化とカテゴリ2段絞り込み(2026-08-15・竹森氏裁定)

**起点の問い**: 「ミシュランは星1〜3がすべてか」「ビブグルマンとは」「星なしの掲載もあるのか」、および「カテゴリが『ステーキ』の店が、別の画面では『洋食』になっている」。

**実測で分かっていたこと**(調査は台帳374行の全数集計):
- 台帳のミシュラン内訳は ★2=1 / ★1=6 / ビブ=24 / 掲載店(sel)=44 / 掲載なし=282。**掲載75店のうち68店は星なし**
- カテゴリは `catGroup`(大分類11)と `cat`(小分類69)の2階建てで、**店ごとに必ず1つずつ・合計2個**。欠落0件、同じ小分類が2つの大分類にまたがる例も0件
- 食い違いの正体は不整合ではなく**画面ごとに出す階層が違った**こと(一覧カード・地図の吹き出し・絞り込み=大分類 / 詳細パネルだけ小分類。しかもラベルは両方「カテゴリ」)

**裁定3件と実装**:
1. **掲載店を地図で見分けられるようにする(A案=色+記号の2信号)**: 淡い金ボディ(`MICHELIN_SEL_BG`)+`Ⓜ`+25px。ミシュランが金系3段(濃い金★ / 琥珀🍽 / 淡い金Ⓜ)のグラデーションになる。凡例にも1行追加。「縁の色だけ」は2026-08-09に見分け不能と判定済みなので採らない
2. **大分類→小分類の2段絞り込み**: 大分類の隣に小分類セレクト(`fCat`)。**大分類が「すべて」の間は disabled**、大分類を選ぶとその中の小分類だけが件数付きで並び、値は必ず「すべて」から始まる。選択肢は台帳から毎回生成(`syncCatSubOptions()`)＝定数表を持たない
   - 小分類も共有リンクに載る(`f=fCatGroup:…|fCat:…`)。選択肢が親に依存するため、復元は info.js が「書く→選択肢を作る→もう一度書く」の2回
   - **4つ横並びだと1つ約90pxになり選んだ値が読めない**(実測)ため、飲食の絞り込み行だけ2列で折り返す(`.filter-row-2col`)
3. **詳細パネルは親子で出す**: 「洋食・グリル ＞ ステーキ」。大小が同名の分類(中東・バー・屋台街)は1つだけ出す

**データ側の防御**: 「小分類は必ず1つの大分類にだけ属する」を `test/dining.test.js` の不変条件にした(またがると、どちらの親から入ったかで結果が変わり選択肢の件数も二重計上になる)。テスト694件green。

## 19. UI/UXのゼロベース見直しと実装(2026-08-16・竹森氏裁定)

**調べ方**: 実データ実測(374行の全数集計) + 実画面計測(本番/ローカルをブラウザで開き座標・幅・コントラスト比を測定) + 利用者タスク歩行 + モック注入 + 390px iframeでのスマホ再現 + supplement-dbからの横展開抽出 + 世界標準調査 + 敵対的検証 + 独立したゼロベース案。提案書=artifact「357軒から1軒を決める」。

### §19追補(2026-08-16・同日の追加裁定2件)

**1. エリアの絞り込みを削除し、その枠に細分類を入れた**
竹森氏「エリア自体はもうマップの上にあるから」。地図上のエリアジャンプ(16ボタン)が
同じ用を足していたため、`fDiningArea` のセレクトを画面から外した。空いた枠には細分類を入れ、
**カテゴリのすぐ右**に置いた(大分類の中をもう一段絞る、という関係が並びで分かる)。
枠の数は4のままで、上段は「カテゴリ / 細分類 / 予算 / ミシュラン」。
細分類の枠は常に置き、中身が決まるまで押せない状態で待つ(枠ごと出し入れすると、
選ぶたびに他の枠が動いてしまう)。
**バケツの判定(`AREA_BUCKETS` / `areaBucketOf`)と対応表は domain 側に残した** —
6班体制の調査で作った「どのエリア名がどの付近に属するか」の知識そのものであり、
捨てると作り直しになるため。`matchesDining` は `f.diningArea` を受け取れば今も効く。

**2. 商業施設と飲食店のピンの重なり**
竹森氏「商業施設が飲食店に潰れてしまっているものがある。商業施設を優先に見せて、
その横にずらして飲食店の数字が出てくる形が望ましい」。
実測: 80m以内に飲食がある商業施設は8件(Pavilion KLは6店)。手当ては3つ。
- **商業マーカーに `zIndexOffset`(=1000)** を与え、常に飲食の上に描く
- **モールに重なる飲食ピン・数字玉は、アイコンだけ右へ32px** ずらす(`.mk-mall-shift` +
  CSSのtranslateX)。**座標は動かさない**ので、選ぶと従来どおり本当の位置が中心に来る
- **判定の半径は縮尺から出す**(`overlapRadiusM`)。重なりは画面上の現象で、引いた地図では
  1pxが何十mにもなるため固定半径だと取りこぼす(ズーム13では1px≒19m)。数字玉は
  ズームのたびに作り直されるので、そのときの縮尺で判定できる
- **ラベルが常時出る縮尺(17)以上ではずらしをやめる**。名前ラベルは本当の座標に付くので、
  ずらしたままだと名前とピンが離れて見える。切り替えは地図コンテナのclassだけで行い、
  マーカーは作り直さない

実測の効果(ズーム15・KL中心): 重なっていた6組すべてで商業が上になり、見た目の重なり面積は
Pavilion 702→234px² / LaLaport 276→36 / Plaza Damas 104→72 / Solaris 160→16、
The Exchange TRX は完全に解消。テスト736件green。

ズームを17以上に上げられず**実画面では未確認**(判定の純関数と配線はテスト済み)。

## 20. 記録をクラウドへ（2026-08-16・データ消失事故を受けて）

**事故**: 竹森氏がスマホで付けた記録が丸ごと消えた。救出も失敗。

**原因（3つとも「別のURLを開いた」ように見える）**:
- **iOS Safari の7日ルール**: サイトを7日開かないと LocalStorage/IndexedDB を自動削除する（Apple の ITP 仕様）
- **アプリ内ブラウザ**（LINE・メール等）は Safari と別の保存領域
- **ホーム画面に追加したアプリ**も Safari のタブと別領域

**設計の穴（こちらが本質）**: バックアップの「フォルダ自動保存」は File System Access API（`showDirectoryPicker`）依存で、**iPhone・Android には存在しない**。つまりスマホは保険ゼロのまま運用していた。画面には「この端末にだけ保存」と出していたが、**それは警告であって対策ではない**。

**裁定（竹森氏）**: 保管先=Firebase／ログインはユーザー名＋合言葉／将来のユーザー管理もこれに乗せる。

**採った構成**:
- Firebase プロジェクト `mkd-dining`（Spark無料・カード不要）。Firestore は `asia-southeast1 (Singapore)`
- 認証はメール/パスワードだが、画面では**ユーザー名だけ**を聞き、内部で `<name>@mkd.local` に変換する
- 記録は `users/{uid}` の1文書に、書き出し封筒（既存のエクスポート形式）をそのまま入れる。既存の parseImport / replaceAll というドアを使うので、personal.js は無改変
- セキュリティ規則は `allow read, write: if request.auth != null && request.auth.uid == uid;` のみ。**公開サイトでも他人の記録は読めない**
- SDK は CDN から**ログインするまで読まない**（住まいモードの速度は不変）

**同期で守る一線（`src/domain/cloudSync.js`・テスト19件）**:
- **片方が空のときしか自動で同期しない**。両方に記録があって中身が違えば、**必ず人が選ぶ**（件数とクラウドの最終更新を出す）。新しい端末で初めてログインした瞬間に空がクラウドを消す、がこの種の同期で最も多い事故
- 書き出し時刻の違いは「変更」とみなさない（毎回衝突が出てしまう）
- 封筒が壊れていたら書かない（復旧できなくなる）
- 0件は書ける（「全部消す」を人が押した結果は正当）
- ログアウトしても端末の記録は消さない

**実ブラウザで通した経路**: 新規作成→アップロード／別端末を再現（記録0＋再ログイン）→ダウンロード復元／衝突→自動上書きせず2択を提示→「この端末を残す」で決着。テスト用アカウントとデータは検証後に削除済み（Authentication・Firestore とも空を目視確認）。

**残した保険**: JSON の書き出し／読み込みは廃止しない。Firebase に何かあっても手元にデータを取り出せる道を必ず残す。

## §22 保存まわりの整頓 — 保存先を1つの物語に（2026-08-16 竹森氏裁定）

**指摘**: 「保存形式、データ管理のところを見ましたけど、複雑です。こんな複雑なことをやる必要あります？ 今の各いろいろとできることを整頓して、究極にシンプルにしてください。昔の仕様も残してるから、こういう形になってます。ログインした状態だったら、何の ID でログインしているかっていうのが見えるようにしてください」
**追加指示**: 「もうオート保存でいい。保存ボタンを押さなければ保存されないのではなく、書き込むごとに常にオート保存され、そして自動的にバックアップを取る形がいい」

### 何が起きていたか（本番のログイン中画面で実測）

| 測ったもの | 実測値 |
|---|---|
| データ管理の縦 | 1,284px（窓593px＝2.2画面）／スマホ390pxで4.4画面 |
| 節・ボタン | 6節・8ボタン |
| 「まだ保存していません」 | **同じ文が3箇所**（保存バー・クラウド節・保存の状態節） |
| 「保存先は◯◯です」 | **3通りが同時表示**（フォルダ／このブラウザ＋ファイル／ログイン中） |
| 保存バー | 幅236pxに4つを連結。必要53pxに対し35pxしか出せず**3行目が黙って切れていた** |

原因は素直に「昔の仕様が残っていた」こと。①localStorage ②フォルダ自動保存（8/8のA案・**スマホには存在しない**） ③クラウド（8/16）が並存し、それぞれが自分の言葉で自己紹介していた。

### 削減案の敵対的検証

「フォルダ自動保存を消す」案を潰しに掛けた結果、**1点だけで潰れた**: `backups/` の日次7世代が、このアプリで唯一の「昨日に戻す」手段。しかも `writeCloud` は `setDoc` の全上書きなので、誤消去は1.2秒でクラウドへ伝わって取り返しがつかない。
→ **保険を先に用意すれば消せる**、と読み替えて実装した。

あわせて検証が見つけたクラウド側の穴（実コードで裏取り済み）:
- `cloudNotifyChanged` が `error` 相で早期returnし、**1度失敗すると以後の記録が無言で届かなくなる**
- `onStatus` が `listView === 'data'` のときしか再描画せず、**クラウド復元で記録が入れ替わっても台帳が古いまま**
- `pushNow` が書く前にクラウドを読まない（2端末同時運用で後勝ち）→ **今回は塞いでいない**（下記）

### 採った形

**保存の物語は1つだけ**: 「記録は書いた瞬間に自動でクラウドへ。控えも自動で溜まる。何も押さなくていい」

- **フォルダ自動保存を全廃**（`src/data/fileStore.js` 262行・`src/domain/fileSync.js` 98行・`test/fileSync.test.js` 113行を削除、`dineFile*` 5ハンドラと1節を撤去）
- **控え（自動）**を新設。判断は純関数 `src/domain/snapshots.js`、保存は `personal.js`（別キー `mkd_dining_snapshots_v1`）
  - `undo` … 全消去・まるごと置き換えの**直前**に1件。押し間違いは直後に気づくので世代は要らない
  - `daily` … その日の最初の変更の**前**＝前日までの姿。7世代
  - 置き場が localStorage なのは、374店に全部感想を書いた最悪ケースで封筒が実測56KB、8世代で451KBになり **Firestoreの1文書上限1024KBに近すぎる**ため。端末の故障・データ消去はクラウドの**本体**が守り、控えが守るのは「自分の操作ミス」で、それは同じ端末で起きる
  - 控えを取るのは**関数の中**（`clearAll`/`replaceAll`）。呼び出し側が忘れられる場所には置かない
  - 控えが保存できなくても記録本体の保存は続く（古い daily を捨てて1度だけ再挑戦し、それでも駄目なら控えを諦める）
- **押す保存を廃止**（「今すぐ保存」ボタンと `dineCloudSyncNow` を削除）。代わりに `error` 相からも次の変更で自動的に書き直す
- **クラウド復元時の再描画**を `listView === 'data'` 条件から外した
- **データ管理は3節**（記録の保存先／控え（自動）／片づけ）。JSONの直接あつかいは畳みの中へ全部入れた
- **保存バーが言うのは2つだけ**。ログイン中は `☁ ユーザー名 ・ 最終保存 HH:MM:SS`、未ログインは `⚠ この端末にだけ保存。消すと失われます`。赤くするのは**壊れているときだけ**（常に赤い警告は、そのうち見えなくなる）
- 全消去の確認は2回→**1回**。戻せるものを2回聞くのはただの摩擦

### 結果（実測）

| | 前 | 後 |
|---|---|---|
| 節 | 6 | **3** |
| データ管理の縦（未ログイン・デスクトップ） | 1,372px | **852px** |
| 同（スマホ390px） | 4.4画面 | **2.7画面** |
| 保存バー | 必要53px / 出せる35px（**切れていた**） | 必要18px / 出せる18px（**切れない**） |
| 誤消去からの復帰 | PCでフォルダ接続時のみ（手作業で `backups/` を開く） | **全端末で[この時点に戻す]1押し** |
| テスト | 770件 | **778件** |

### 実画面で通した経路

記録2店 → 全消去 → 控えに「消す直前（2店）」→[この時点に戻す]→ 2店に復帰、を実ブラウザで確認。

### 塞いでいない穴

`pushNow` が書く前にクラウドを読まない（PCとスマホを**同時に開いたまま**両方で記録すると、後で書いた方の封筒が丸ごと勝つ）。読み取り→突合→衝突提示を足す必要があり、今回の整頓とは別の変更。deferred-backlog に記載。

## §24 Google のクチコミへ1タップで（2026-08-18 竹森氏「リンクが切れていませんか」「ワンクリックで飛べるように」）

### 何が起きていたか

リンクは**切れていたのではなく、4分の3の店に最初から無かった**。

`src/ui/info.js` の `googleMapsUrl()` は、Place ID が `pending:` で始まる店に対して空文字を返す。「無い ID で別の店を開くくらいなら、リンクを出さない」という正しい設計。問題はデータ側で、**生存365店のうち280店（76.7%）が `pending:`** のまま置かれていた。うち274店は★評価を持っていたので、画面には評価だけが黒い文字で出て、押せなかった。

原因は 2026-08-09 の飲食350店拡充。店は増やしたが Place ID の採取は後回しにされ、backlog に「Places API無しでは取得不能。いつかまとめてブラウザ実機で採取する」と書かれたまま残っていた。**テストは全green**だった — `test/diningLayer.test.js` が「pending の店はリンクを出さない」を仕様として固定していたので、280店にリンクが無くても誰も落ちない。

### やり方を選び直した

backlog の前提「Places API無しでは取得不能」が**誤り**だった。Google マップの内部検索（`/search?tbm=map`）は素の HTTP で JSON を返し、その中に **店名・緯度経度・Place ID・CID** が入っている。鍵も課金も要らない。

別の店を掴まないための関門を2つ置いた（`tools/fetch-place-ids.js`）:
1. **距離** — 台帳の（検証済みの）座標から、building 250m / venue 450m / street 700m 以内
2. **名前** — 正規化して一致すること

どちらか欠けたら採らず `review` に落とす。

**この道具を、まず既にIDが在る85店で答え合わせした**（`--check`）。結果 83件を採用し、うち80件は元のIDと完全一致。残り3件は食い違ったので1件ずつ Google マップを開いて確かめたところ、**3件とも「元のIDが間違っていた」**（Ushi→SUSHI TAKA、Nipah→EQ ホテルそのもの、Marta's Kitchen→ただの通り）。つまり採用83件の的中率は100%で、おまけに既存データの誤りが3件見つかった。

作る途中で2つの罠を潰した。**「Ushi」が「SUSHI TAKA」に部分一致して別の寿司店を掴んだ**ので、前方一致は語の切れ目でしか認めないようにした。**「Bōl」と「Bol」「Café」と「Cafe」が別語として落ちた**ので、アクセント記号を畳むようにした。

### 結果（実測）

| | 件数 |
|---|---|
| 自動で採れた | 266 |
| 人が1件ずつ見て決めた（`tools/place-id-manual.json`） | 11 |
| **入った合計** | **277 / 280** |
| 既存IDの誤りを直した | 3 |
| pending のまま（裁定待ち） | 3 |

採用277件の距離は**中央値0m・90%が69m以内・最大355m**。店名が完全一致/前方一致でないものは12件で、全て「Dominic → Restaurant Dominic」の類。

残る3件と、この作業で判明した**台帳の座標誤り4件**（最大2,568m）は deferred-backlog の 2026-08-18 節が正。

### 押した先を概要からクチコミへ
