# mont-kiara-dashboard 刷新計画

作成日: 2026-08-07 ／ 状態: **裁定待ち（未着手）**

このアプリは「KL・ペナンで、どこに住み、どこに通わせ、どこで買い、どこで食べるか」を1枚の地図で決めるための道具です。
この文書は、いまの姿・見づらさの原因・直し方・進め方をまとめたものです。

---

## 1. いまの姿（2026-08-07 実測）

`index.html` ただ1ファイル、1,210行。中身はCSS 151行・HTML 99行・JavaScript 950行。
外部ライブラリは地図の Leaflet 1.9.4 だけ。最終更新は 2026-04-26。

載っているデータは **392件**。

| 種別 | 件数 | 元ファイル |
|---|---|---|
| 物件（コンドミニアム） | 271 | `condos_data.csv` |
| 商業施設 | 88 | `commercial_data.csv` |
| 学校 | 33 | `schools_data.csv` ＋ `schools_detail.json`（ペナン9校の詳細） |

これに、別ファイルの飲食店台帳（`kl-dining-ledger-v9.html`・50店）を加えるのが今回の目的です。

### 無いもの

README、テスト、lint、CI、`package.json`。開発の土台が丸ごとありません。
画面側も、aria属性 0・セマンティックHTML 0・`onclick` 直書き 30箇所・URLに画面状態が乗らない（リロードで選択が消え、リンクで共有できない）。

## 2. 見づらさの原因は3つ

### 原因1 — 3種類の別物を1つの箱に入れている

コードの1201行目にこれがあります。

```js
CONDOS = [...CONDOS, ...COMMERCIALS, ...SCHOOLS];
```

物件・商業・学校を1つの配列にまとめ、同じ形として扱っています。
そのため学校のデータには「luxTier: D」「家賃: 0」といった意味のない値が入り、
商業施設の「テナント名」欄を、学校では「カリキュラム」の表示に流用しています。

ここが、後の2つの原因の根っこです。

### 原因2 — 地図が読めない

392件すべてに常時ラベルが出るため、KL中心部は文字が重なって判読できません。
これは初期表示の状態です。ここに飲食50件を足すと、さらに悪化します。

### 原因3 — 絞り込みが物件専用のまま全部にかかる

フィルタは8個ありますが、すべて物件向け（Luxury Tier・Sale PSF・家賃・広さ…）。
学校を見ているときも「Luxury Tier」が選べてしまい、逆に
学校の「カリキュラム」「学費」「対象年齢」、商業の「テナント」、飲食の「料理ジャンル」で絞る手段が1つもありません。

### もう1つ、信頼性の問題

データは GitHub の生ファイルURLから実行時に取得し、失敗すると
第三者のCORSプロキシ `allorigins.win` を経由する作りになっています。
公開サイトの読み込み経路に他社サービスが入っている状態です。データをサイトに同梱すれば消えます。

### 放置ファイル

`calc.js` / `luxury_calc.py` / `recovered_data.txt` の3つは、git未追跡かつどこからも参照されていません（grep確認済み）。
うち2つは62物件ぶんのハードコード写しで、CSVと値がずれています（例: MK11 の家賃上限 20,000 vs CSV 22,000）。

## 3. 直し方 — 「主役1つ ＋ 環境3層」

いま4つのデータセットが横並びですが、実際に答えたい問いは
**「ここに住んだら、暮らしはどうなるか」** です。

そこで役割を変えます。**物件が主役。学校・商業・飲食は周辺環境のレイヤー。**
逆引き（この学校に通わせるならどの物件か／この店の近くに何が住めるか）も、同じ仕組みで成り立ちます。

### 打ち手5つ

| # | やること | 効くこと |
|---|---|---|
| M1 | 層タブ（物件／学校／商業／飲食）を1本立てる。選んだ層が主役、他は薄い背景 | 一度に見る情報が1/4になる |
| M2 | 地図の整理 — 背景の層はクラスタにまとめ、ラベルはズーム14以上と、指したとき・選んだときだけ。形でも区別する（物件=円／学校=角丸／商業=菱形／飲食=ピン） | 地図が読めるようになる |
| M3 | 絞り込みを層ごとに分ける | 「関係ないフィルタ」が消える |
| M4 | 詳細に「周辺」タブ — 緯度経度から 徒歩圏(≤800m)／車5分(≤2km)／車15分(≤6km) で相互に表示 | 見て終わりにならない |
| M5 | URLに画面状態を乗せる（`?layer=condo&id=...&tab=nearby`） | 戻る・リロード・共有が壊れない |

M4は既存の School Finder が持つ「3km以内の物件」を捨てずに、全種別へ広げたものです。

その副産物として、物件カードに **「徒歩圏: 学校2／モール1／星付き3」** という一行を出せます。
数えるだけなので、独自の合成スコアを発明せずに済みます。

### 層ごとの絞り込み（M3の中身）

| 層 | 絞り込み軸 |
|---|---|
| 物件 | tier / PSF / 家賃 / 広さ / 築年 / 権利（FH/LH） / 状態 |
| 学校 | カリキュラム / 年間学費 / 対象年齢 / 生徒数 |
| 商業 | NLA / アンカーテナント / 開業年 |
| 飲食 | **料理カテゴリ** / ミシュラン / 価格帯 / エリア / 施設種別 / 子連れ可 / 訪問状態 |

## 4. 飲食店の統合

**方針: 1アプリ2モード（2026-08-07 裁定）**

同じ地図・データ層・周辺エンジンを共有したうえで、

- **住まいモード** … 飲食は周辺環境レイヤーとして表示（「この物件の徒歩圏に良い店があるか」）
- **外食モード** … 台帳v9の全機能を維持（訪問記録・予算・感想・賛否抜粋）

個人の記録は localStorage に隔離し、丸ごとエクスポート／削除できるようにします。
公開サイトとしても使うため、この分離は必須です（他人には自分の記録は見えない）。

### 必須要件（竹森氏 2026-08-07 明示）

| # | 要件 | 現状 |
|---|---|---|
| 1 | 訪問したか / していないか | v9に実装済（`ST[id].v`）→ **継承** |
| 2 | また訪問したいか | v9に実装済（また行く／機会があれば／もういい の3択）→ **継承** |
| 3 | 1人あたりの予算 | v9に実装済（`ST[id].amt`・ヘッダーに実額平均）→ **継承** |
| 4 | 感想 | v9はメモ1行のみ → **複数行に拡張** |
| 5 | 行ったことがある店をまとめる | v9の「Log」タブに実装済 → **継承・強化** |
| 6 | 食事のカテゴリーで選べる | **未実装。今回の新規** |

### カテゴリ分けの案（要裁定）

現在の `cat` は50店で **33種類**に分散しており、そのまま並べても選べません。
実データを数えて、8つの大分類にまとめる案です（合計50件で検算済み）。

| 大分類 | 件数 | 含まれるもの |
|---|---|---|
| マレーシア料理 | 12 | モダン・マレーシアン5／ニョニャ3／ニョニャ・マレー／マレー・ジャワ／マレー／ナシレマ |
| 洋食・グリル | 10 | フレンチ3／炭火・薪火2／イタリアン／モダン・ヨーロピアン／ヨーロピアン／グリル／ボーダーレス |
| 中華 | 6 | 広東・点心2／広東（老舗）／中華（モダン）／客家（擂茶）／焼味 |
| インド・スリランカ | 6 | インド2／南インド（菜食）／北インド／バナナリーフ／スリランカ |
| 鶏飯・ご飯もの | 5 | 土鍋鶏飯3／海南鶏飯2 |
| 麺・肉骨茶 | 5 | 麺2／肉骨茶2／魚頭麺 |
| 日本・その他アジア | 5 | 日本料理2／タイ／ベトナム／中東 |
| 屋台街 | 1 | 屋台街 |

論点2つ:
- 「中東」を “その他アジア” に入れているのは無理がある。件数が増えたら独立させる。
- 「屋台街」1件は単独の分類として弱い。将来ホーカー系が増える前提なら残す、増やさないなら他へ寄せる。

### 前提となる作業

**飲食50店には緯度経度が1件もありません。** Google Place ID と住所しか持っていません。
地図に載せるには Place ID からの座標取得が先です。ここが取れないと、飲食はリスト表示止まりになります。
飲食統合の最初のゲートに置きます。

## 5. 構造のブラッシュアップ

他リポジトリ（gic-order / 竹森English / gic-core）から抽出した現行ルールとの差分です。

| 家ルール | 現状 | 対応 |
|---|---|---|
| SSOTスキーマ1本 | 3種別が1配列に混在 | 型別コレクション＋共通 `PlaceBase`（id / type / name / nameJa / lat / lng / addr / area / url）に分離 |
| 名前での参照は改名で壊れる | 全結合が `name` 文字列 | 安定ID（C0001 / S0001 / M0001 / R0001）を付与。nameは表示専用に |
| 計算はSSOTで一本化 | luxScore がコード埋込＋古い写しが2ファイル | 純関数に切り出し、契約書に文章で固定し、テストで守る |
| テスト / lint / CI | 全部なし | Vitest ＋ GitHub Actions。**作って終わりにせず green を確認する** |
| 契約書・引き継ぎ資料 | READMEすら無い | README / CLAUDE.md / CONTRACTS.md / CODEBASE-MAP.md |
| URL＝画面状態 | なし | M5 |
| 整合性チェック（異常0） | なし | 座標範囲・ID重複・数値逆転（min>max）・参照切れ |
| 巨大ファイルを作らない | 1ファイル1,210行 | 機能ごとに分割。行数ガードはバックストップとして1本 |

**技術スタック（2026-08-07 裁定）: Vite ＋ 素のJavaScript ＋ Vitest。**
Leaflet が命令型APIで素のJSと相性が良く、442件規模ではReactの利点が小さい割に950行の書き直しコストが実費で出るため。

## 6. 進め方

| 段階 | 内容 | 見た目 |
|---|---|---|
| **P0 即効＋土台** | M2（地図の整理）を先行実装。ゴミ3ファイル削除。Vite / Vitest / CI 導入。データをサイトに同梱してCORSプロキシ経路を撤去 | ★地図が読めるようになる |
| **P1 データ層** | 型分離・安定ID・インライン重複データのファイル化・計算SSOT・整合性チェック | 変化なし（土台） |
| **P2 情報設計** | M1 / M3 / M4 / M5 | ★本命の見やすさ |
| **P3 飲食統合** | 50店の座標取得 → 飲食層追加 → 外食モード（要件1〜6） | ★飲食が乗る |
| **P4 品質** | a11y・モバイル・OGP・出典表示・資料整合 | 仕上げ |

M2をP0に前倒しするのは、P0-P1が「見た目が何も変わらないのに重い」状態になるのを避けるためです。
M2は既存構造のままでも効きます。

データ精度の向上（飲食を10-20%から拡充、既存物件の再検証）は別トラックです。
検証手順は既存メモリにあるものをそのまま使えます（EdgeProp優先／pool=0は73%が誤り／premium_scoreは加重式）。

未反映の指摘が1件あります: `recovered_data.txt` 内の Le Nouvel KLCC（premium_low_density=3・premium_score=14 が正、CSVは2/13のまま）。

## 7. 自己採点

提出前の5工程（ルーブリック採点 → 複数案比較 → 敵対的自己レビュー → 極端ケース → 採点表明示）を実施済み。

| 観点 | 点 | 理由 |
|---|---|---|
| ①シンプルさ | 8/10 | 概念は1つ増えるが、画面あたりのコントロール数は減る |
| ②データ量・使い方への適合 | 9/10 | 442件、将来900件を前提に設計 |
| ③ネクストアクションが浮かぶ | 9/10 | 周辺タブ・徒歩圏カウント。合成スコアは保留 |
| ④誰が・いつ使うか | 9/10 | 4用途すべてと確定（住まい探し／来訪者案内／家族の台帳／公開サイト）。当初6点から改善 |
| ⑤世界標準との照合 | 8/10 | Zillow・Rightmove の amenity layer、Walk Score 的な近接表示、Leaflet cluster はいずれも標準手法 |
| ⑥既存仕様の継承 | 9/10 | School Finder の「3km以内の物件」を周辺エンジンへ昇格。エリアジャンプ・比較・日英併記・戻る動線を維持 |
| **計** | **52/60** | |

### 潰した敵対3点

1. **「P0-P1は見た目が変わらないのに重い。順序が逆では」**
   → M2だけP0に前倒しして即効性を確保。P2の情報設計は型分離に全面依存するため、順序自体は変えられない（混在配列のままUIを作ると作り直しになる）。
2. **「4層＋2モードで、結局複雑になっただけでは」**
   → 認知負荷は「同時に見えるコントロール数」で測る。現状の8ドロップダウン無差別適用より減る。
3. **「個人記録を住宅ダッシュボードに持ち込むのは筋が悪い」**
   → 部分的に正しい。だからモードを分け、個人データは localStorage 隔離＋丸ごと削除可にする。住まいモードには個人記録を出さない。

### 極端ケース

- **最大ズームアウト＋全層ON** = 442マーカー常時ラベル。**これが今の初期表示**で、実機で判読不能を確認済み。M2が必須である根拠。
- **飲食が500件に増えた場合** = 名前結合・全件DOM描画・全件マーカーが破綻する。安定IDとクラスタを最初から入れる理由。
- **飲食に座標が無い** = 50件全部。P3の最初のゲート。取れなければ飲食はリスト止まり。
